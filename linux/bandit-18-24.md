# OverTheWire Bandit — Levels 18 to 24

**Platform:** OverTheWire | **Category:** Linux / CLI | **Difficulty:** Beginner | **Date:** 10/10/2026

## Objective

Continue through Bandit by investigating restricted SSH behavior, SUID executables, localhost networking, cron jobs, shell scripts, and brute-forcing a four-digit PIN against a local service.

## Level summary

| Level | Concept | Key command |
|-------|---------|-------------|
| 18 → 19 | Bypass the forced logout by running a remote command over SSH | `ssh bandit18@bandit.labs.overthewire.org -p 2220 cat readme` |
| 19 → 20 | Use a SUID program to run a command with its owner's privileges | `./bandit20-do cat /etc/bandit_pass/bandit20` |
| 20 → 21 | Use a listener and a SUID client that checks a password sent over localhost | `nc -l -p 1234` and `./suconnect 1234` |
| 21 → 22 | Inspect a cron job that copies a password to a temporary file | `cat /etc/cron.d/cronjob_bandit22` |
| 22 → 23 | Reproduce a hash-based filename generated by a cron script | `cat /tmp/$(echo I am user bandit23 \| md5sum \| cut -d ' ' -f 1)` |
| 23 → 24 | Write an executable shell script for a cron job to run | `chmod +x getpass.sh` |
| 24 → 25 | Try all 10,000 four-digit PINs over one netcat connection | `seq -w 0000 9999 \| ... \| nc localhost 30002` |

## What I learned

**Running a remote SSH command (Level 18 → 19):**

The normal interactive SSH login immediately logged me out because the account's shell startup configuration was designed to do that. Instead of requesting an interactive shell, I passed a command directly to SSH: `ssh ... cat readme`. SSH authenticated me, ran the command on the remote machine, printed its output, and then ended the session. This taught me that SSH can be used for remote command execution as well as interactive login.

**SUID : what it means and why it matters (Level 19 → 20):**

SUID stands for *Set User ID*. It is a special permission bit on an executable file. Normally, a program runs with the permissions of the user who launched it. When an executable has SUID enabled, it runs with the effective user ID of the file's owner instead. For example, if a SUID executable is owned by `bandit20`, running it as `bandit19` can make that program perform permitted actions as `bandit20`. In this level, `./bandit20-do` let me run a command with the file owner's privileges and read the password file for the next level. SUID is not automatically a vulnerability; the risk appears when a privileged program allows unsafe or unintended actions.

**A localhost listener and a SUID client (Level 20 → 21):**

The `suconnect` program connects to a port on localhost and checks whether the text received over that connection matches the previous level's password. I started a listener with `nc -l -p 1234`, then ran `./suconnect 1234` in another terminal. Sending the correct password through the listener allowed the program to return the next password. This level connected network fundamentals with Linux permissions: the listener and client communicated over TCP on the same machine, while the SUID program's privileges made the result possible.

**Cron : scheduled jobs and trust (Levels 21 → 22, 22 → 23, and 23 → 24):**

`cron` is a service that runs commands automatically on a schedule. A cron configuration specifies when a job runs and which command or script it should execute. The files in `/etc/cron.d/` contain system cron-job definitions, so reading the relevant file tells me what runs and under which account.

In Level 21 → 22, the scheduled script copied the `bandit22` password into a temporary file and set permissions that allowed me to read it. In Level 22 → 23, the script generated a temporary filename by hashing the text `I am user bandit23`. I reproduced the same calculation with `md5sum` and extracted the hash using `cut`, which let me find the file without guessing its name.

In Level 23 → 24, the cron job ran as `bandit24`, processed eligible scripts placed in `/var/spool/bandit24/foo/`, and removed each submitted script after processing it. I wrote a Bash script that read `/etc/bandit_pass/bandit24` and redirected the output to `/tmp/saim_password`, made the script executable, and copied it into the spool directory. The cron job ran the submitted copy with its own account's permissions, and I read the resulting output file. I kept my original script in a separate working directory because the submitted copy was deleted.

**Shell scripting and output redirection (Level 23 → 24):**

A shell script is a text file containing commands that the shell runs in order. The line `#!/bin/bash` identifies Bash as the interpreter, and `chmod +x` adds execute permission. The redirection operator `>` sends a command's standard output into a file, replacing that file's previous contents. These basic pieces were enough to automate the task instead of typing the commands manually.

**Brute-forcing a four-digit PIN (Level 24 → 25):**

The service on `localhost:30002` required the `bandit24` password followed by a secret four-digit PIN. Since the PIN could be any value from `0000` through `9999`, there were 10,000 possibilities. A loop using `seq -w 0000 9999` generated every candidate, and each line was formatted as `password PIN`. Piping all the lines into one `nc localhost 30002` invocation sent the guesses over a single connection, as the level instructed. The successful response contained the password for the next level. The `-w` option matters because PINs can begin with zero.

**The broader privilege-escalation lesson:**

I hit the same underlying idea twice now — once via a CTF mechanic (SUID/cron), once via a real backdoor (vsftpd) — something running with more trust than the person operating it is the common thread across most privilege escalation.

SUID and cron are legitimate Linux features, but they can create security problems when privileged programs or scheduled jobs trust unsafe inputs. The vsftpd 2.3.4 backdoor was a different case: a deliberately backdoored service could provide a shell with excessive privileges. The shared lesson is to ask which account or privilege level a process runs as, what inputs it trusts, and whether a less-privileged user can influence its behavior.

## Where I got stuck

**Level 18 → 19:** The interactive SSH session closed immediately, which initially made it seem like I could not log in. The useful change was to send the command as part of the SSH invocation rather than trying to get an interactive shell. This helped me understand that the remote command can still run even when the normal login shell is not usable.

**Level 20 → 21:** The important part was coordinating the two sides of the connection. The listener had to be running on the chosen localhost port while `suconnect` connected to it. Thinking of it as a client and server exchanging one line of text made the sequence easier to understand.

**Level 22 → 23:** I needed to notice that the temporary filename was not random. The cron script deterministically calculated an MD5 hash from the text `I am user bandit23`. Once I copied the exact input and reproduced the same hash pipeline, I could locate the password file.

**Level 23 → 24:** I initially checked `/tmp/saim_password` before the cron job had finished creating it, so the file did not exist yet. I also received `Permission denied` when trying to list `/var/spool/bandit24/foo/`; that restriction did not prevent the job from processing the script I had successfully copied there. The key was to verify the output file separately and remember that the cron job deletes submitted scripts after execution. Nano's warning about its missing history directory was harmless and did not prevent the script from being saved.

**Level 24 → 25:** The brute-force task was about automating repetitive input rather than manually trying PINs. Generating all values with `seq -w` and piping them into one netcat process avoided creating a new connection for every guess. Preserving leading zeros was essential because `0042` is a four-digit PIN, not the shorter string `42`.
